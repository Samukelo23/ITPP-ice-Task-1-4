Reflection

Looking back on this module

Note to self: this is a first draft written from the outside. Read it over and rewrite the parts that don't sound like you — especially the strongest-skill and skill-to-improve sections, which only you can really answer.

This module has been my first real experience of building software from a written brief rather than a small isolated exercise. Working through assignments like QuickChat meant thinking about a system as a whole — how a message is stored, how it's retrieved, how a menu option connects to the logic underneath it — rather than just getting a single function to run. That shift, from "does this line work" to "does this system hold together," is probably the biggest thing I've taken away from the module.

I also learned to take testing seriously rather than treating it as an afterthought. Writing JUnit tests for edge cases — a duplicate entry, an action on something that doesn't exist, a limit being reached — forced me to think about how a program should fail, not just how it should succeed. That habit has already changed the way I write code: I find myself asking "what happens if this is empty, or wrong, or missing" much earlier than I used to.

If I'm honest about where I'm currently strongest, it's probably in structuring a problem before I start coding — breaking a brief into classes and responsibilities, and getting the object-oriented design right before worrying about the console menu wrapped around it. Where I still want to improve is in writing genuinely thorough tests, rather than just enough to cover the obvious cases. I tend to test the path I expect someone to take, and I want to get better at deliberately trying to break my own code before someone else does.

To work on that, I'm planning to make test-writing a habit I do alongside development rather than after it — sketching out the cases I expect a feature to be tested against before I write the feature itself. I'd also like to look more closely at how experienced developers structure their test suites, rather than writing tests purely from instinct.

This portfolio gives that progress somewhere to live. As I take on more modules and projects, I can add to it rather than letting finished work disappear into old assignment folders — and by the time I'm applying for internships or graduate roles, it should be a reasonably honest record of what I can actually do, not just what I say I can do.
